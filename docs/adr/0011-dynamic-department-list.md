# ADR-0011: Department List as a Table, Not a Fixed Array

## Status
Accepted

## Problem
`employees.department` was validated against a hardcoded, 9-value array duplicated in `server/src/modules/employees/constants.js` (server enforcement) and `server/public/shared/orgConstants.js` (frontend dropdowns). Real CEAS departments — "AI & Innovation", "Traffic Management" — weren't in that list at all, so employees in those departments could never be correctly assigned one; whatever free-text value ended up in the column just fell into the Teams directory's "Other" bucket with no way to fix it short of a code change and a deploy.

## Decision
Replace the fixed array with a `departments` table (`id, code, label, active, created_at`) that `manager`, `people_culture`, `operations`, and `admin` can add rows to at runtime through the Roster page, and rename in place (`code` never changes after creation — only `label`, the display name). `employees.department` gets a real `FOREIGN KEY ... REFERENCES departments(code)` — not just a service-layer check — since a real table now exists to reference. Every frontend consumer (roster table, Add Employee form, Account Settings, the signup wizard, the Teams directory, My Team) fetches the live list from `GET /api/employees/departments` (open to any authenticated user, and pre-auth for the signup wizard — department names aren't sensitive, same tier as the employee directory) instead of reading the static array. Only `POST`/`PATCH` are gated server-side to the four roles above, inside `departmentService.requireCanManage` — the same pattern `rosterService.canManageRoster` and `conflictPairService.requireCanManage` already use in this module.

An initial version of this feature also let a department be deactivated (soft-delete), matching this module's `conflict_pairs`/`employees` "revoke, never delete" convention. That was removed before shipping: deactivation only reduced friction for a scenario (a typo'd name) that in-place rename handles more directly, and — worse — offered no way back once a department was deactivated. Renaming the `label` in place fixes the actual problem (a wrong or missing display name) without ever needing to hide or retire a row, so the `active` column is left in the schema (harmless, always `1` going forward) but nothing in the app sets it to `0` anymore.

Adding the FK required a full SQLite table rebuild of `employees` (SQLite can't `ALTER` a FK onto an existing column), using the identical technique `004_add_people_culture_role.js` already used to change `users.role`'s CHECK constraint. Any employee row whose department didn't match a known code (the exact free-text/mismatched-case values that motivated this decision) was backfilled into its own `departments` row first, verbatim as `code`, so the rebuild never fails and no employee's existing assignment is silently dropped.

## Alternatives considered
- **Keep the array, just add the two missing departments** — rejected. Doesn't solve the actual problem: the next new department still requires a code change and a deploy, and whatever real value already exists in the affected employees' rows still isn't handled.
- **Add departments to the array via an admin-editable config file/env var, no DB table** — rejected. Still requires a deploy (or at least a restart) to pick up a file change, and doesn't give per-department state (active/inactive) or an audit trail the way a real table with `audit.record(...)` calls does.
- **Service-layer validation only, no DB-level FK** — considered, since it's simpler and avoids the table-rebuild risk. Rejected because `department` already had zero enforcement of any kind before this table existed, and now that a real table exists there's no reason not to guard it the same way every other `employees` FK already is (`user_id`, `manager_employee_id`) — a write that bypasses `rosterService` entirely (a future script, a different code path) would otherwise still be able to write garbage into the column.

## Trade-offs
- The `employees` table rebuild is the highest-risk step in this change — it's the single most-referenced table in the schema. Mitigated by testing the exact migration against a full copy of the real database first and taking a fresh `backup:snapshot` immediately before deploying (see the migration's own comments).
- Renaming only ever changes `label`, never `code` — two departments created with very different names that happen to slugify to a colliding `code` can't both exist (`create` rejects the collision), but there's also no way to fix `code` itself later short of retiring the row conceptually (nothing stops creating a new one with a better name and reassigning affected employees, same as the removed deactivate flow would have required). This is an accepted gap: `code` collisions are rare (the slugifier is deterministic and label-derived) and `code` is never user-facing.
- Legacy free-text values backfilled by the migration keep their original (sometimes messy) casing/spelling as their `code` and a mechanically title-cased `label` — the label half of that can now simply be edited via the same rename flow, so this is a one-time cosmetic cleanup rather than a structural gap.

## Consequences — explicit revisit trigger
Reconsider this ADR if departments ever need more structure than a flat, renamable `label` — a parent/child hierarchy, per-department settings, or a need to actually retire one that's no longer in use (which would require deciding how to handle employees still assigned to it, the exact question deactivation used to answer before it was removed). Until then, a flat, role-manageable table with create/rename is the smallest change that fixes the actual reported problem.
