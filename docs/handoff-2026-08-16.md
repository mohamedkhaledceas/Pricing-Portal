## What shipped today

**Step 1 — Schema + shared bucket-mapping module**
New tables `commercial_lead_bucket_events` and `commercial_lead_quarter_snapshots`; a new `origin_quarter` generated column on `commercial_lead_live_cache`; new `commercialLeadBuckets.js` (status → funnel bucket mapping). Caught a real bug: `PRAGMA table_info` silently omits generated columns, which would have crashed the server on every second restart — fixed by switching the existing idempotency check to `PRAGMA table_xinfo`.

**Step 2 — Live event capture**
`clickupSync.js` now writes to the new events ledger on every real bucket-crossing, reusing the same "our own observed timestamp" convention the existing `stage_history` table already uses (not any ClickUp-supplied field).

**Step 3 — One-time historical backfill**
`commercialLeadBackfill.js`, run for real: 190/196 deals backfilled, 6 quarterly snapshots frozen (2025-Q1 → 2026-Q2). Two real bugs caught by testing against real data:
1. `"in queue "` (real trailing space in ClickUp's status value) was silently unmapped, dropping those deals from the funnel entirely.
2. The originally-approved identity-matching field (`Company`) turned out to be CEAS's own internal business line (~102/152 deals = "Ceas Comm"), not client identity — produced a false 100% repeat-client rate. Fixed by switching to `Client Name ` per your direction.

**Step 4 — Live dashboard**
New route `GET /api/commercial-lead/quarterly-kpis`; the old "0 new leads today" tile replaced with the full 9-metric KPI row (Leads, Qualified, Onboarding, In Progress, Conversion 1, Conversion 2, Won, Lost, Repeat Client Rate) plus quarter navigation. Verified live in a browser: numbers match hand-calculation, nav boundaries correctly disable, zero console errors, no regression elsewhere on the page.

**Step 5 — Freeze job**
`commercialLeadFreeze.js` — fires at each Cairo-local quarter boundary via `node-cron`'s native `timezone` option (independently cross-checked against this project's own SQL-side DST approximation — they agree exactly), plus a startup catch-up call so a missed boundary self-heals on next boot. Dashboard now shows a small "at close: X" annotation under any tile where the frozen and live figures have actually diverged — verified with a real synthetic divergence test, not just a same-value fresh case.

## Investigated: ClickUp shows 13 "leads", the dashboard's current-quarter tile shows 19

Checked this against the real data — **both numbers are correct, they're just answering different questions**, not a bug:

- **13** = how many deals, across the *entire* 2026 Projects list, are sitting in the raw `leads` status **right now**, regardless of when they were created. (This is also what the dashboard's own "Pipeline by status" chart shows — same number, same meaning.)
- **19** = the cohort size for Q3 2026 — how many deals were **created** this quarter, regardless of current status. Of those 19, only 3 are still actually in `leads` status; the rest have already moved on (7 qualified, 3 in queue, 1 onboarding, 1 in progress, 2 stuck, 1 unqualified, 1 lost).

This is the cohort model working exactly as designed — a "Leads" tile that means "pitches made this quarter" (matching how you originally framed the whole feature: "how many pitches are made, to how many are winning pitches"). But the label alone doesn't make that distinction obvious, and this is exactly the kind of thing someone will keep tripping over. Worth either renaming the tile (e.g., "Pitches" or "New This Quarter") or adding a tooltip clarifying it's a cohort count, not a live status count — your call on which.
